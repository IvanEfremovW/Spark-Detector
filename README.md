# Spark-Detector

# 1. Данные

## 1.1. Существующие датасеты

Были рассмотрены варианты датасетов в открытом доступе, в частности несколько датасетов с Roboflow ССЫЛКА, но большинство из них имеет критические недостатки:

- Кадры всего датасета взяты из одного видео. (Например, [ARK2](https://universe.roboflow.com/robo-wntxy/arc2-kmj2s/browse?queryText=+sort%3Afilename&pageSize=200&startingIndex=800&browseQuery=true))
- Кадры одного видео попадают и в train, и в val, и test выборки датасета, что вызывает data leakage, поэтому требуется вручную перераспределять данные.
- Датасеты практически не включают кадры искр других производственных инструментов, кроме сварочных аппаратов.

## 1.2. Собранный датасет

На основе этих датасетов было принято решение собрать собственный набор данных используя видео с YouTube, RuTube ССЫЛКИ и отдельные части найденных датасетов для сварки (в частности [welding detection](https://universe.roboflow.com/kodifly-b2nmn/welding_detection-w9t9j)).

Для уменьшения количества ложных срабатываний я старался включать в датасет изображения, содержащие источники освещения, такие как лампы или окна. Часть таких изображений не содержит искр и является набором контрпримеров для модели.

Собранные данные размечались вручную, используя инструменты Roboflow.

## 1.3. Аугментации

Цветовые для адаптации к различным условиям съёмки:
- hsv_h 0.015 - Изменяет оттенок (Hue) на +-1.5%
- hsv_s 0.7 - Изменяет насыщенность (Saturation) на +-70%
- hsv_v 0.4 - Изменяет яркость (Value) на +-40%

Геометрические для инвариантности детектора к размеру и положению объектов:
- mosaic 1.0 - Объединяет 4 изображения в одно (2x2 сетка)
- fliplr 0.5 - Горизонтальное отражение с вероятностью 50%
- degrees 10.0 - Поворот изображения на +-10 градусов
- translate 0.1 - Сдвиг изображения на +-10% по X и Y
- scale 0.5 - Масштабирование на +-50%

# 2. Решение

## 2.1. Выбранная архитектура

В качестве прототипа решения было принято решение использовать базовую архитектуру детекции с использованием модели **YOLO26**. 

Модели YOLO зачастую являются идеальным компромисом между качеством и скоростью, а так же хорошо работают с признаками разных масштабах (искры могут быть как большим шлейфом, так и маленьким снопом).

Учитывая объём данных и скорость обучения, была выбрана s версия модели. При необходимости для большей точности систему можно легко масштабировать, используя модели m/l/x, но для этого требуется сбор большего объёма данных для того, чтобы избежать переобучения.

## 2.3. Анализ ошибок и Bottlenecks

### Плохая обобщающая способность

Главная проблема системы - из-за малого количества и специфики собранных данных модель работает слишком узконаправлено.

В частности большая часть изображений сварки, собранных из открытых источников, содержит яркое синее свечение и небольшой сноп искр, как можно видеть на примерах в 1.2.

На результатах тестовых видео видно, что модель достаточно хорошо запоминает подобные признаки.

На предоставленных же видео сварка значительно отличается внешне, происходит domain-shift и модель не справляется с детекцией на этих примерах:

- [test_sparks_easy_result.mp4](https://drive.google.com/file/d/1Z6hn47YPOdbdwJCSc6jue0BSMZMRZvrB/view?usp=sharing)

- [test_sparks_medium_result.mp4](https://drive.google.com/file/d/1lpx0gH2z3uVWN9B_SwvD_aDjWcZsNhBa/view?usp=sharing)

Эта проблема должна быть легко разрешима добавлением большей вариативности данных с реальных производственных съёмок.

### Пропуск индивидуальных искр

Модель обучена детектировать **снопы иск**. Это приводит к тому, что детекция часто пропускает отдельно летящие искры.

### False Positive на предоставленном видео

## 2.4. Предлагаемое развитие

### Использование специфики данных

Помимо улучшения датасета обучения модели можно так же поработать с предобработкой данных.

Стандартная детекция не учитывает важную специфику данных: мы работаем с видео, следовательно, имеем возможность использовать характеристики искр в динамике, а не только на статичном изображении.

В качестве улучшения базовой архитектуры предлагается использовать две таких характеристики:

1. **Яркость** - искры чаще являются самым ярким объектом на изображении
2. **Движение** - искры являются движущимся объектом

Использование этих характеристик в отдельности представляет сложности, но при совместном использовании они хорошо дополняют друг друга.

Например, очевидной проблемы использования фильтра по яркости является то, что он будет реагировать на источники освещения. Но факт того, что искры всегда движутся, позволяет использовать вычитание фона, оставляя для рассмотрения только динамические объекты.

И обратно, использование только фильтра по движению будет оставлять на видео перемещение людей, станков и т.д. Использование фильтра яркости позволяет не обращать внимание на движущиеся объекты, не подходящие по яркости.

Поэтому предлагается ввести создание маски для каждого кадра изображения на основе **фильтрации по яркости** и **вычитанию фона** и уже далее применять алгоритмы детекции.

Подобная предбработка реализована в модуле `preprocessing.py`. Для тестирования при запуске с помощью аргументов `--use-preprocessor` и `--use-detector` можно выбрать, какие элементы пайплайна будут запущены - детектор, обработка или всё вместе. 

Примеры действия на тестовых видео:

- [cutting_masked.mp4](https://drive.google.com/file/d/1yqK7MYURqoo0YV9_OpKjzSC3JFZXWIhA/view?usp=sharing)

- [welding_masked.mp4](https://drive.google.com/file/d/1wZWOYGczzYwVEdVwameSXqI3e98dhMtN/view?usp=sharing)

### Возможные проблемы

Создание полноценной системы детекции с использованием этих улучшений требует предобработки и переразметки всего датасета.

Так же использование подобных фильтров предполагает определённые требования к оборудыванию:

- Камера должна иметь хорошую стабилизацию, чтобы видео не имело сильной встряски
- Камера должна хорошо адаптироваться к резким изменениям яркости при начале/окончании работы инструментом.

Большая часть видео в открытом доступе не обладает этими характеристиками. Они снимаются из рук и чаще всего на камеры любительского уровня.
# 5. Установка и запуск

Взаимодействие с системой реализовано через CLI.

## uv

1. Перейти в папку проекта

2. Установить зависимости
```bash
uv sync
```
3. Запустить
```bash
uv run src/spark-detector/main.py \
  -i path_to_input \
  -o path_to_output \
  -m models/path_to_model \
  --use-preprocessor \
  --use-detector
```

## Docker 

**1. Предварительные требования**

- Установлен Docker.
- Установлен NVIDIA Container Toolkit (для использования GPU).

**2. Сборка**
```bash
sudo docker build -t spark-detector .
```
**3. Запуск**

>[!important]
>При запуске на **windows** требуется заменить `$(pwd)` на `${pwd}` для корректной работы
```bash
sudo docker run -it --rm --ipc=host --gpus all \
  -v $(pwd)/models:/app/models \
  -v $(pwd)/data:/app/data \
  spark-detector \
  -i /app/data/path_to_input \
  -o /app/data/path_to_output \
  -m /app/models/path_to_model \
  --use-preprocessor \
  --use-detector
```
